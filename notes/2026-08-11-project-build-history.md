## 第八段：這個專案是怎麼一步步被造出來的（含踩過的坑）

從 git 紀錄看，這個專案是分幾個階段疊上去的，我照順序帶你看，重點是**每個坑背後代表什麼道理**，不只是「哪裡出錯」。

### 第 0 步：先把骨架搭起來

第一個 commit「Initial implementation」，一次把整個 deterministic-first 管線的骨架、加上 n8n 編排都寫出來——也就是我們前七段講的三層引擎、n8n 流程、docker-compose。這是「先讓東西能動」的階段。

### 坑 1：n8n 匯入流程要「可以重來」

**問題：** 一開始的計畫是用滑鼠在 n8n 網頁介面上手動匯入 workflow、手動用下拉選單指定「發生錯誤時要跑哪個錯誤處理流程」。這種做法有個致命缺點——**別人 clone 這個 repo 下來，沒辦法用一行指令重現整個設定，得照著截圖一步一步手點**。

**解法：** 讓兩個 workflow 的 JSON 檔都帶「固定 ID」，讓主流程直接在設定裡寫死「我的錯誤處理流程 ID 是這個」。這樣一來，用指令列匯入這件事變成**冪等操作**（idempotent——不管執行幾次，結果都一樣，重複執行不會出錯或製造重複資料）。這是工程師很在意的一個特質：**任何設定步驟都應該能用一行指令重現，而不是依賴「人記得要點哪裡」**。

### 坑 2：n8n 傳檔案給 API，欄位名對不上

**問題：** n8n 收到上傳的檔案後要轉手交給 FastAPI，結果一直報錯「找不到叫 `file` 的欄位」。

**真正原因（很陰）：** n8n 的 Webhook 節點在處理檔案上傳時，會**自己偷偷把你設定的欄位名加上一個數字**——你叫它 `file`，它內部實際存成 `file0`。這不是你哪裡打錯字，是 n8n 這個工具本身的行為，第一次遇到的人幾乎都會被誤導去檢查自己的設定。

**這個坑教會我們的事：** 串接兩個不同系統時，**「同一個詞」在不同系統裡不見得代表同一件事**——n8n 內部叫這個資料的名字，跟 FastAPI 端點認得的欄位名，是兩條互不相干的命名規則，你要分別搞懂、分別對上，不能想當然爾覺得兩邊寫一樣就會通。

同一次還發現：n8n 新版把「啟用（Active）」這個按鈕改名叫「發佈（Publish）」了，而且**沒發佈的錯誤處理流程會被「靜默跳過」**——畫面上完全看不出異狀，只有系統日誌裡藏著一行不起眼的「is not active」。這種「看起來像設定對了，其實某個開關沒開，而且不會主動告訴你」的狀況，在維運系統時很常見，也是為什麼「有沒有實際端到端跑一次、看它真的動了」比「畫面上看起來設定完了」更重要。

### 坑 3：表單上的變數沒有被代換

**問題：** 審核員打開表單，該顯示文件 ID 的地方，看到的是**原始的 `{{ $json.document_id }}` 這串程式碼**，而不是真正的 ID。

**原因：** n8n 有個規則——**一個欄位的值，前面要加一個 `=` 符號，n8n 才會把裡面的大括號語法當成「要去代入變數」，不然就當成一段死的文字**。少了那個 `=`，畫面上就會原封不動顯示你寫的程式碼片段。

**修好之後**，順便把整條「人工審核」的路徑完整跑了一次：上傳一份故意缺欄位的文件 → 系統判斷要轉人工 → 表單正確顯示出文件 ID 和被標記的欄位 → 人工填寫修正 → 流程真的「醒過來」繼續跑 → 修正值被寫回資料庫 → 審計紀錄裡看得到「改了什麼」。**這種端到端（end-to-end）跑一次，比單獨測試每個小零件更重要**——因為每個零件單獨看都對，串起來才會踩到「這個小地方漏了一個等號」這種細節。

### 坑 4：一句「應該更省」在被實測之前，只是一個猜測

這是我覺得最值得學的一點。「規則層優先」這個設計理念在專案一開始就寫進架構文件了，聽起來很合理——但**合理不等於真的省**，在真正做實驗量測出數字之前，這只是一個「假設」。

第一次真的跑對照實驗時，發現數字對不起來——規則層組別的準確率比預期少了一筆（332/334 而不是預期的數字）。查下去發現：**評估用的資料庫沒換乾淨**，裡面殘留了剛剛示範人工審核流程時、已經被人手動改過的一筆紀錄。因為系統設計成「同一份文件（用檔案的 SHA-256 雜湊值判斷）重送會直接回傳之前存的結果，不會重新跑一次」（這是為了避免重複花錢重新分析同一份文件），結果評估腳本把「人工修正過的答案」誤當成「AI 自己抽取的結果」去計分，數字就失真了。

**解法很直接：** 換一個乾淨的資料庫重跑，並且在 README 加一句警語提醒未來的人。**這個坑教會我們的事：一個為了效率而設計的機制（相同文件不重複處理），在另一個情境下（評估準確率）可能變成陷阱**——設計一個功能時想清楚它的優點，但也要記得它在別的用途下可能悄悄污染資料。

換乾淨資料庫重跑之後，才拿到我們前一段看到的那組真實數字：79.5% 免費解決、省 67% 成本、快 58 倍。

### 坑 5-7：收尾階段

後面幾步是收尾性質：把架構圖從純文字 ASCII 圖換成正式的 SVG 向量圖、把 README 裡每一句話**逐項對照原始碼和截圖**重新核對一遍（唯一發現的落差是某張截圖裡 p95 延遲跟表格數字對不太上——判斷後認定這是「兩次呼叫真實 GPT-4o Vision API，網路延遲本來就會抖動」，不是文件寫錯，這種「即時外部服務的延遲每次量都不完全一樣」是要事先跟讀者說清楚的，不是拿一次的數字當成鐵律）。

最後原本規劃錄一支示範用的 60 秒 GIF，籌備過程中又挖出一個坑——**n8n 的「等待人工審核」節點，它的審核連結是「執行到那一步的當下才臨時產生」的，不是一個固定網址，你沒辦法事先準備好連結**，得先去系統的執行紀錄頁面找到那筆「正在等待中」的紀錄，才能拼出正確網址打開表單。這比想像中麻煩，後來這支 GIF 決定先不錄，但把「怎麼拼那個網址」的方法留在筆記裡，之後真的要錄還是有步驟可以照做。

如果要用一句話講這整個過程教會我的事：**「聽起來合理」和「量測出來是真的」是兩回事**，這個專案幾乎每個階段的坑，都是「以為設定對了/以為這樣做會更好，結果實際跑一次才發現有落差」——不管是 n8n 一個沒打的等號、資料庫沒清乾淨污染了實驗數字，還是「規則層真的比較省嗎」這種核心賣點本身，都需要**實際端到端跑過、拿真實數字驗證過**，才能放心寫進 README 裡當作事實。這也是為什麼這個專案的評估章節這麼被重視——履歷上寫的每個數字，背後都對應著一次真的重跑過、換過乾淨資料庫的實驗，不是憑印象估的。
